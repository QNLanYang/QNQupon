# 架构与设计决策

## 前言

-  **为什么核销不需要身份认证？**

  - 本系统的优惠券采用“不记名凭证”模型：券码本身就是权益，谁持有有效券码，谁就可以核销。二维码只是券码的载体，作用等同于一张纸质优惠券或提货券。店员扫码并确认核销，表示这次权益已在现场完成兑换。

  - 我们不要求核销者登录、实名或绑定账号，是因为目标场景是个人、小商户和熟人环境，例如“朋友到亲戚小店免费喝一瓶可乐”。这个场景追求的是低门槛、零学习成本、现场快速完成。若为核销者增加身份认证，就需要账号、权限、登录、找回等一整套体系，成本和复杂度会超过优惠券本身的价值。

  - 这也意味着：系统无法判断扫码的人是持券人、店员，还是看到/拍到二维码的其他人。系统只判断券码是否有效、是否还有次数。因此，请像保管现金或纸质券一样保管二维码。券码被截图、转发、公开或偷拍后，他人扫码核销会视为一次有效使用并扣减次数，通常无法撤销或补发。

  - 核销记录用于查询和对账，记录核销时间、券码、剩余次数等信息，但不作为身份证明，也不承诺追责。若发生误核销，建议商户与持券人线下协商处理。

  适用边界：本设计适合低价值、熟人、现场核销的优惠券；不适合高价值、公开投放、可兑换现金或强合规场景。后者应增加店员登录、核销口令、动态二维码、地理围栏、实名绑定等机制。

## 总览

单进程 Fastify 应用，服务端渲染 HTML + 一份 `app.js`/`app.css`，SQLite（WAL）持久化，无任何外部服务依赖（SMTP 按需启用）。

选型理由：

- **better-sqlite3（同步驱动）**：没有连接池与异步交错，"条件 UPDATE 是否影响行数"天然是并发判定的原子边界，核销正确性简单可证
- **服务端渲染、零构建**：自托管场景不需要 SPA；无前端依赖、无打包步骤，`public/` 两个文件就是全部前端
- **重活出关键路径**：邮件发送失败不回滚核销；PNG 渲染放独立子进程（见下）

## 数据模型（8 张表）

| 表 | 作用 | 关键设计 |
| --- | --- | --- |
| `users` | 两级账号 | `role ∈ {super_admin, business_admin}`，`active` 停用即吊销会话 |
| `sessions` | 后台会话 | 只存 token 的哈希 + 与会话绑定的 `csrf_hash`，过期时间 `SESSION_HOURS`（默认 12 小时） |
| `coupons` | **券面** | 自增整数 ID；`starts_on/expires_on` 为日期字符串（自然日）；`status ∈ {active, disabled, recycled}` |
| `voucher_codes` | **券码** | 主键为 `cd-` + 12 位随机 ID 的 TEXT；`token_hash`（唯一）+ `token_ciphertext`；`used_count` 带 `CHECK(used_count >= 0)`；`show_name` 券码名显示覆写（NULL 跟随全局、1 显示、0 隐藏） |
| `redemptions` | 核销记录 | 每次核销一行：时间、来源 IP、UA、邮件状态、唯一 `confirmation_code` |
| `presets` | 建券预设 | 说明/门店文案模板 |
| `app_settings` | 键值设置 | `encrypted` 标记的值用 AES-256-GCM 加密存储（如 SMTP 密码） |
| `audit_log` | 审计 | 操作者（可为空，如失败登录）、动作、目标、IP、详情 JSON |

券面/券码为 `ON DELETE CASCADE`：永久删除券面会连带其券码与核销记录。

## 券面 + 券码两级模型与 ID 策略

- **券面用自增 ID**：后台内部资源，序号可读无风险，方便讨论与排查
- **券码用 `cd-` + 12 位 base62 随机 ID**（拒绝采样保证均匀，≈71 bit）：
  1. 不可枚举、不暴露发码数量（自增序号会泄露"这家店发过多少张"）
  2. 路由层先做格式校验（`/^cd-[A-Za-z0-9]{12}$/`），不符直接 404——把随机 ID 当成第一层模糊防护
  3. 冲突时重试 3 次
- 券码可用性 = 自身状态 **∧** 券面状态：查询时 join 合成判定，停用/回收券面即让全部券码失效，不需要逐张写回
- **创建券码**：单张与批量共用同一入口与表单（`createCode` / `createCodes`，批量 1-100 张）。批量名称统一为「基名 #序号」，序号左补零到与本次数量同宽（9 张 → `#1`…#9，100 张 → `#001`…#100）；未给基名则按「券面名、券面名 #1…」碰撞取号（中间被删/回收的号会被补上）。批量券码名显式设为不显示（`show_name = 0`，单张仍可覆写或跟随全局），整批一个事务、一条 `code.batch` 审计

## Token 设计：哈希 + 加密副本并存

每张券码一个 256 bit 密码学随机 Token，是核销 URL `/r/<token>` 的唯一凭证。库里存两份：

| 存储 | 用途 | 泄库后果 |
| --- | --- | --- |
| `token_hash`（SHA-256，唯一索引） | 核销时 O(1) 查找比对 | 只有哈希，拿不到可用 Token |
| `token_ciphertext`（AES-256-GCM，密钥在 `.env`） | 重建二维码/重新导出券面 | 需同时拿到 `.env` 密钥才可解 |

只存哈希无法还原二维码（运营上"重新下载二维码"是刚需），只存明文则泄库即泄核销权——所以两份并存、各取所长。

**Token 永不出现在后台 HTML 里**：「复制核销链接」点击时才从需要登录的 `/admin/codes/:id/link` 接口取值；配合 `Referrer-Policy: no-referrer`，Token 不随任何请求外发。

## 核销流程

1. `GET /r/:token` 只读展示（次数、日期、直白的可用性原因），**绝不改状态**
2. `POST /r/:token/redeem` 执行核销：
   - 原子扣减：`UPDATE voucher_codes SET used_count = used_count + 1 WHERE id = ? AND status = 'active' AND 未过期 AND 未到开始日 AND used_count < max_uses`——**以 `changes === 1` 为成功判据**，并发抢兑只有"次数"那么多能成功（测试：并发 12 次只成功 5 次）
   - 成功后插入 `redemptions` 一行，生成唯一 6 位确认码（32 字符集，去掉 `0/1/I/O`，`xxx-xxx` 展示格式；输入端容忍大小写/空格/连字符）
   - 触发 SMTP 通知（失败只标记 `email_status = failed`，**不回滚核销**）
3. 结果页：成功绿色面板放大确认码，失败红色面板写直白原因（用尽/过期/未生效/停用）

## 状态机与生命周期

- 数据状态只有三档：`active` / `disabled` / `recycled`；展示态在其上合成（含"未到开始日"→未启用、日期判断→已过期、次数判断→已用尽）
- 列表状态徽章固定五色：可核销（绿）、已用尽/已过期（黄）、未启用（蓝）、已禁用（红）、回收站（灰）
- 每小时维护任务：
  1. 到期或用尽**满 N 天**（`recycleDays`，默认 30、后台可调）的券面/券码 → 移入回收站（`recycled`）
  2. 回收站**满 N 天**（`purgeDays`，默认 30、后台可调） → 永久删除（CASCADE 连带券码与核销记录）
  3. 到期执行每日备份
- 回收站页面独立（券面/券码两栏），可一键恢复；只有超级管理员勾选确认后可永久删除

## 时间与日期

- 一律 UTC ISO 存储
- **有效期按 `Asia/Shanghai` 自然日**比较（`YYYY-MM-DD` 字符串语义："截止 12 月 31 日"= 12-31 当天仍可用）
- 页面展示统一经 `beijingTime` 转北京时间
- 理由：运营语义是自然日而非精确时间戳；避免服务器时区不同导致"过期时间漂移"

## 核销凭证查询（防伪）

- `GET /verify`（HTML 表单，结果 URL 可分享）+ `GET /api/verify/:code`（JSON，**不带 CORS 头**；字段 `found / confirmationCode / faceName / codeName / redeemedAt / redeemedAtBeijing`，调用示例见 [README](../README.md)）
- 默认保留 72 小时可查（`verifyHours`，后台可调）；JSON 只回上述最小字段，HTML 结果页另显示邮件通知状态——IP、UA、备注、核销链接一概不返回
- 结果页层级：确认码缩为顶部小标题，真伪结论与券面/券码/核销时间/邮件状态放大为视觉重心，底部「查询下一个」返回查询表单
- 过期、查不到、从未核销统一中性灰面板（不泄露"码存在与否"以外的信息）；格式错才给明确红提示
- 两入口各限流 30 次/分/IP；HTML/JSON 均 `Cache-Control: no-store`（防查询结果被缓存串号）
- 设计动机：**可信域名查询接口 + SMTP 主动通知 = 最低成本的防伪组合**，威胁模型详见 [SECURITY.md](../SECURITY.md)

## PNG 券面渲染（子进程）

- `png-render.js`（父进程）↔ `png-child.js`（子进程）走 NDJSON stdin/stdout 协议，base64 传回图片
- **不缓存**、按需生成；队列串行执行压低峰值；**队列上限 20**，超出直接 429
- 单张 30 秒超时；最后一次渲染 **60 秒后子进程自动退出**，sharp/libvips 占用的内存全额归还系统（实测子进程峰值 ~90 MB → 退出后 0；主进程稳定 ~72 MB）
- 版面：文字区与二维码区严格分离（二维码永不被文字遮挡）；二维码含 Token → 响应 `no-store`

## 前端约束（与 CSP 的关系）

严格 CSP（`script-src 'self'` 等，零放宽项）意味着模板**不得出现内联 `<script>`、`style=` 属性、`onclick=` 等**——否则浏览器直接拒绝执行。新增页面必须遵守，这是硬约定（另见 SECURITY.md 响应头表）。

模态确认框自实现（动态生成 DOM、`textContent` 填充），不依赖 `window.confirm`——防止被浏览器或微信内置 WebView 拦截；确认文案经 `data-confirm-title` / `data-confirm` 指定，同时保留按钮原生 `formaction` 与必填校验。
